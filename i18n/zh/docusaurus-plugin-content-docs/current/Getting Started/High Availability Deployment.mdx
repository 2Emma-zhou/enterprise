## 方案目标

在离线或私有化环境中部署一套 Tier0 企业版，总计使用6台虚拟机：

- 3台：应用节点。组成 `Docker Swarm` 集群基座，承载 Tier0 企业版单副本服务和 **EMQX** 有状态服务
- 2台：数据库节点。组成 `PostgreSQL + TimescaleDB` 主从集群
- 1台：`Witness` 节点。参与数据库监督、仲裁和故障切换

:::note 可选
- 引入外部 `NFS/NAS` 共享存储，供三台 Swarm 节点挂载，用于 Tier0 企业版跨节点共享文件。
- 该共享存储是外部依赖，不计入本方案6台业务虚拟机。
:::

:::info
本方案假设每台数据库虚拟机规格为 `4C / 8G / 500G`。若用户实际要求为数据库集群合计 `4C / 8G / 500G`，则需要在实施前重新核算性能和容量。
:::

## 总体拓扑

<img width={650} src="http://enterpriseimage.oss-cn-hangzhou.aliyuncs.com/image.png" />

:::info
图中只表达核心链路。
:::
- 业务访问路径：用户 / 现场系统 -> `APP VIP` -> 三台 `Docker Swarm` 节点 -> `DB VIP` -> 当前主库
- 图面按南北向从上到下排列，表现请求进入、应用处理、数据库访问和高可用监督关系
- 拓扑图不展示集群内部端口、SSH 运维链路和监控链路，统一放到<a href="#连接方式清单">连接方式清单</a>和<a href="#端口明细清单">端口明细清单</a>中
- `Witness` 只参与数据库仲裁、选主和健康检查，不在业务访问路径中
- `APP VIP` 直接分发到三台 Swarm 节点，并统一通过 `DB VIP` 访问数据库
- `APP VIP` 漂移在三台 Swarm 节点之间，`DB VIP` 随当前 PostgreSQL Primary 角色在两台数据库节点之间漂移
- Tier0 企业版按单副本服务运行，节点故障后由 Swarm 调度到其他健康节点重启
- `EMQX` 是有状态服务，不按普通无状态服务随机漂移；默认应固定节点持久化，若要求消息层高可用则部署三节点 EMQX 集群
- 可选 `NFS/NAS` 只作为 Swarm 节点共享文件存储，不进入主数据库请求链路

#### 关键边界：

- `Witness` 不承载业务数据，不参与业务读写，也不对应用开放数据库访问
- 业务只连接 `DB VIP:5432`，禁止直连 `ent-db-01/02`
- `DB VIP` 必须绑定当前 PostgreSQL Primary 节点，不能仅以数据库进程存活作为漂移依据
- `TimescaleDB` 作为 PostgreSQL 扩展部署在两个数据库节点上，不单独拆库
- 建议采用 `PostgreSQL streaming replication + repmgr + repmgr witness + keepalived DB VIP`
- 自动故障切换只处理主库不可用场景；原主库恢复后先作为备库重新加入，不自动抢回主库

**关键口径：**

- Tier0 企业版可以单副本运行，Swarm 只提供集群基座和故障漂移能力
- `EMQX` 不能简单套用 Tier0 企业版的单副本随机漂移策略，因为它有会话、订阅、保留消息、规则引擎状态和持久化目录
- 如果 `EMQX` 只部署单节点，应明确它是消息层单点，并固定到一台 Swarm 节点的持久化目录
- 如果业务不能接受 `EMQX` 单点，应在三台 Swarm 节点上部署三节点 EMQX 集群，并为每个节点配置固定主机名，节点名和持久化目录

### NFS/NAS 共享存储口径

引入 NFS 的目的，是为了 Tier0 企业版单副本在 Swarm 节点之间漂移后仍能访问同一份业务文件。它不改变数据库主从和 EMQX 有状态服务边界。

**适合放到 NFS 的内容：**

- 用户上传附件
- 导入 / 导出文件
- 报表文件
- 离线包、模板、可再生成的中间文件
- 需要跨节点读取的业务静态文件

**不建议放到 NFS 的内容：**

- PostgreSQL / TimescaleDB 数据目录、WAL 目录
- EMQX 核心数据目录、Mnesia 数据、运行时状态
- Docker Engine 数据目录 `/var/lib/docker`
- 高频数据库型写入、锁敏感文件、强一致队列

**NFS 边界：**

- NFS 是共享文件依赖，不是数据库高可用组件
- NFS 本身如果是单点，会成为文件功能单点；生产建议使用已有 HA NAS 或双控存储
- Tier0 企业版单副本漂移到其他 Swarm 节点前，目标节点必须已挂载并验证 NFS 可读写
- 如果 Tier0 企业版完全不写本地文件，可不引入 NFS

## 服务部署建议

### Docker Swarm

- 三台应用节点均作为 `manager + worker`
- Tier0 企业版以 `docker stack deploy` 发布
- Tier0 企业版默认 `replicas: 1`，Swarm 负责在节点故障后重新调度到其他健康节点
- Tier0 企业版容器不保存关键持久数据，业务数据统一进入 PostgreSQL/TimescaleDB
- Swarm 节点只有 `100G` 存储，按单块系统盘使用；Docker 数据目录保留在系统盘内，不单独规划数据盘
- 配置文件使用 `Docker config`
- 密码、数据库口令、证书私钥使用 `Docker secret`
- 镜像仓库建议使用现场内网 registry，避免部署依赖公网
- 发布时建议配置健康检查，避免入口转发到未就绪容器
- 如应用需要跨节点共享文件，将共享目录挂载到 NFS/NAS，禁止依赖容器本地临时目录保存关键文件
- 需要配置镜像、容器日志和构建缓存清理策略，避免 `/var/lib/docker` 占满系统盘

**单副本部署示例口径：**

```yaml
deploy:
  replicas: 1
  restart_policy:
    condition: any
  update_config:
    order: stop-first
```

### EMQX 有状态服务

`EMQX` 需要按有状态服务处理，不能简单作为普通 Swarm 无状态副本随机漂移。

<table>
  <thead>
    <tr>
      <th>模式</th>
      <th>推荐场景</th>
      <th>部署口径</th>
      <th>风险</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>单节点固定模式</td>
      <td>小规模、能接受消息层短时不可用</td>
      <td>固定部署到 <code>ent-swarm-01</code>，使用本地持久化目录和备份</td>
      <td><code>ent-swarm-01</code> 故障时 EMQX 不自动无损漂移</td>
    </tr>
    <tr>
      <td>三节点集群模式</td>
      <td>正式生产、不能接受 EMQX 单点</td>
      <td>三台 Swarm 节点各运行 1 个 EMQX 节点，固定 hostname、node name 和数据目录</td>
      <td>需要额外配置集群端口、证书、节点发现和监控</td>
    </tr>
  </tbody>
</table>

**单节点固定模式最低要求：**

- 使用 Swarm placement constraint 固定节点，例如 `node.labels.emqx == true`
- 数据目录固定到宿主机，例如 `/data/emqx`
- 配置、证书、插件、规则引擎配置纳入备份
- 节点故障时按“恢复原节点优先，其次从备份恢复到新节点”处理，不做无状态式随机漂移

**三节点集群模式最低要求：**

- 每台 Swarm 节点固定一个 EMQX 实例
- 每个 EMQX 节点使用固定 node name，不随容器重建变化
- 集群通信端口只在三台 Swarm 节点之间开放
- Dashboard 只对运维网段开放
- MQTT 入口可通过 `APP VIP` / 独立 MQTT VIP / 四层负载均衡暴露，实施前需明确入口方式
- 不建议把 EMQX 核心数据目录放到 NFS；EMQX 单节点固定模式应优先使用固定节点本地盘并做好备份，三节点模式依赖 EMQX 自身集群机制

### NFS/NAS 共享存储

- NFS/NAS 为可选外部依赖，不占用六台 VM 名额
- 三台 Swarm 节点统一挂载同一个共享目录
- 只承载 Tier0 企业版需要跨节点访问的共享文件
- 不承载 PostgreSQL/TimescaleDB 数据目录
- 不承载 EMQX 核心运行数据
- 需要配置启动前挂载检查，避免服务漂移到 NFS 未挂载节点后写入本地目录
- NFS 故障时，数据库读写不受影响，但上传、导入导出、报表等文件功能可能失败

### APP VIP

- `APP VIP` 建议使用 `keepalived + HAProxy` 或 `keepalived + Nginx`，部署在三台 Swarm 节点
- VIP 只作为统一入口，不单独占用虚拟机
- 健康检查应以应用 `/health` 或 `/ready` 为准
- 任一 Swarm 节点故障时，VIP 漂移到其余健康节点

### PostgreSQL + TimescaleDB

**建议基线：**

- PostgreSQL：`16` 或现场认证版本
- TimescaleDB：选择与 PostgreSQL 主版本匹配的稳定版本
- 主从复制：物理流复制
- 故障切换：`repmgrd + witness`
- 数据库入口：`DB VIP`
- 连接池：优先在应用侧或单独容器内使用 `PgBouncer`，避免数据库连接数过高

### Witness

- `Witness` 节点仅保存 `repmgr witness` 元数据，用于辅助数据库故障判断和仲裁
- `Witness` 不承载业务数据，不参与业务读写，也不对应用开放数据库访问
- `Witness` 需要稳定网络，不要求高存储性能
- `Witness` 故障不应中断当前业务访问，但会降低自动切换可信度
- `Witness` 恢复后必须验证其重新加入数据库集群状态

## 备份、监控与巡检

**最低交付要求：**

- 数据库每日全量备份，至少保留 `7` 天
- WAL 归档或增量备份，满足现场 RPO
- 每月做一次恢复演练，验证备份可用
- Swarm 服务健康检查、容器重启次数、节点磁盘、内存、CPU 纳入监控
- EMQX 连接数、订阅数、消息吞吐、队列堆积、规则引擎失败、持久化目录使用率纳入监控
- NFS 可用性、挂载状态、容量、inode、读写延迟纳入监控
- PostgreSQL 主从延迟、复制槽、WAL 堆积、连接数、慢 SQL、数据库膨胀纳入监控
- VIP 当前归属、repmgr 集群状态、Witness 状态纳入巡检

**建议巡检命令：**

```bash
docker node ls
docker service ls
docker stack ps tier0-enterprise
ssh ent-db-01 'repmgr cluster show'
ssh ent-db-01 'psql -h 10.60.20.10 -p 5432 -c "select now();"'
ssh ent-db-01 'ip addr show | grep 10.60.20.10'
```

## 实施顺序

1. 创建 6 台 VM，固定主机名、IP、时间同步和 SSH
2. 初始化系统基线、防火墙、磁盘挂载和内核参数
3. 如引入 NFS/NAS，先完成共享目录、权限、挂载和重启自恢复验证
4. 部署三节点 Docker Swarm
5. 部署 `APP VIP + HAProxy/Nginx`
6. 按单节点固定或三节点集群模式部署 EMQX
7. 部署 PostgreSQL + TimescaleDB 主备
8. 部署 repmgr witness、repmgrd 和 DB VIP 漂移脚本
9. 发布 Tier0 企业版单副本 stack
10. 执行连通性、NFS 读写、EMQX 恢复、数据库故障切换、备份恢复和巡检验证
11. 固化运行文档、账号凭据归档和日常巡检任务

## 风险与待确认项

- 现场真实网段、网关、DNS、NTP、证书和镜像仓库地址待确认
- Tier0 企业版是否需要本地文件持久化尚未确认；若需要，应补共享存储或对象存储方案
- NFS/NAS 是否由现场已有存储提供待确认；若 NFS 是单点，会成为共享文件功能单点
- Swarm 节点仅 `100G` 单系统盘，必须控制镜像数量、容器日志和临时文件；不适合承载长期业务数据
- `EMQX` 是有状态服务，需在实施前确认采用“单节点固定”还是“三节点集群”模式；单节点固定模式下消息层存在单点风险
- 数据库 RPO/RTO 未确认，当前方案按主从自动切换设计，不能承诺零数据丢失
- `DB VIP` 的漂移脚本需要在现场验证，特别是虚拟化平台是否允许 VRRP
- 如果现场网络不允许 VRRP，需要改为负载均衡器、DNS 切换或虚拟化平台浮动 IP
